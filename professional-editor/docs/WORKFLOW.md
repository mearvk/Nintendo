# Worked Example — editing the synthetic sample ROM

This walks the full **dump → script → apply → verify** loop using the original
synthetic ROM under [`../samples/`](../samples/). No copyrighted content is
involved; `sample.nes` was generated by this project's own tooling with
placeholder strings.

## 1. The sample ROM

`samples/sample.nes` is a minimal valid iNES image (1 PRG bank, 1 CHR bank) with
these ASCII strings placed at known PRG offsets (file offset = `0x10` + PRG
offset):

| Slot | File offset | Length | Original |
|---|---|---|---|
| menu item | `0x110` | 12 | `START GAME` |
| menu item | `0x120` | 12 | *(empty)* |
| text | `0x140` | 16 | `HELLO WORLD` |

## 2. Dump

```sh
c/nes-edit dump samples/sample.nes 110 12      # -> "START GAME.."
c/nes-edit dump samples/sample.nes 140 16      # -> "HELLO WORLD....."
```

`.` is how the decoder renders padding / non-printable fill bytes.

## 3. Script

`samples/demo.edit`:

```
# Edit the synthetic sample ROM's menu items and text
find 110 12 START GAME
menu NewGame 110 12 NEW GAME
menu Load     120 12 LOAD
set  140 16 GREETINGS ALL
```

The `find` line is a guard: if `0x110` does not currently decode to
`START GAME`, the whole apply aborts and nothing is written.

## 4. Apply (to a working copy)

```sh
c/nes-edit   apply samples/sample.nes samples/demo.edit samples/out.nes
cpp/nes-edit-cpp apply samples/sample.nes samples/demo.edit samples/out.nes
java -cp java/build/classes com.mearvk.nintendo.editor.NesEditCli \
     apply samples/sample.nes samples/demo.edit samples/out.nes
```

All three produce the **same bytes**. The original `sample.nes` is never
modified.

## 5. Verify

```sh
c/nes-edit dump samples/out.nes 110 12   # -> "NEW GAME...."
c/nes-edit dump samples/out.nes 140 16   # -> "GREETINGS ALL..."
```

## Character tables (`.tbl`)

Most real NES games don't store ASCII; they use a game-specific tile encoding.
Supply a `.tbl` so text is read/written in that encoding:

```sh
c/nes-edit dump samples/tbl-sample.nes 110 10 samples/demo.tbl   # -> "MENU      "
```

In a script, add a `table` line before the edits:

```
table samples/demo.tbl
find 110 10 MENU
set  110 10 ITEMS
```

> **Path note.** A `table <path>` in a script is resolved relative to the
> **current working directory** of the tool, not the script's location. Run the
> tool from a consistent directory (e.g. the repo root or `samples/`) so the
> table path resolves the same way across the C/C++/Java tools.

## Safety demonstrations

```sh
# Over-length replacement is refused; output is NOT written:
printf 'set 110 12 THIS IS WAY TOO LONG\n' > /tmp/bad.edit
c/nes-edit apply samples/sample.nes /tmp/bad.edit /tmp/x.nes   # exit 1, aborts

# A wrong find-guard aborts the whole edit:
printf 'find 110 12 WRONGTEXT\nset 110 12 X\n' > /tmp/badfind.edit
c/nes-edit apply samples/sample.nes /tmp/badfind.edit /tmp/y.nes   # exit 1, aborts
```

## The SLeeLa model

Before touching bytes, the SLeeLa model validates a plan against the slot
invariant and prints an OK/REFUSE verdict per edit:

```sh
# from the SLeeLa repo (needs the sleela runtime on PATH):
sleela run sleela/NesEditModel.sleela
```

It is the "think first" layer: express the renames, confirm each fits its slot,
then hand the OK edits to a byte tool as a `.edit` script.
