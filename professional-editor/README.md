# NES Professional Editor

A professional, multi-language toolkit for editing **text and menu items** in
Nintendo Entertainment System (NES) ROM images — in **C, C++, SLeeLa, and
Java**. Part of the `mearvk/Nintendo` studio.

> **Legal & scope.** This toolkit ships **no copyrighted ROM content**. It is a
> clean-room editor that operates on the public, documented **iNES** file format
> ([`docs/FORMAT.md`](docs/FORMAT.md)) so you can edit a ROM image **you already
> own**. The sample ROMs under [`samples/`](samples/) are original, synthetic
> images generated by this project's own tools — not game dumps.

## What it does

- **Read iNES images** — header, PRG-ROM / CHR-ROM regions, mapper, trainer.
- **Edit text** — decode and replace fixed-width text slots in PRG-ROM.
- **Edit menu items** — named, length-bounded menu-label slots.
- **Character maps** — optional `.tbl` tables so text is read/written in a
  game's own tile encoding (not just ASCII).
- **Safety invariant** — a replacement, once encoded, must fit the original
  slot length (shorter is padded). The editor never relocates data or rewrites
  pointers, so the ROM stays structurally valid.

## The four implementations

| Language | Location | Role |
|---|---|---|
| **C** | [`c/`](c/) | `nes-edit` CLI + `libnesrom.a` — the reference byte editor |
| **C++** | [`cpp/`](cpp/) | `nes-edit-cpp` CLI + `libnesrom_cpp.a` — RAII C++17 edition |
| **Java** | [`java/`](java/) | `NesEditCli` + `NesRom`/`CharTable` — JDK-only, Java 21 |
| **SLeeLa** | [`sleela/`](sleela/) | `NesEditModel.sleela` — the editing-model / strategy layer |

All byte tools (C, C++, Java) accept the **same edit-script grammar** and produce
**byte-identical output** for the same script (verified). SLeeLa expresses the
editing *model and strategy* — validating each planned edit against the slot
invariant — because the SLeeLa VM's file surface is string-oriented, not
raw-byte; it hands the validated plan to a byte tool as a `.edit` script.

## Edit-script grammar (shared)

```
# comment
table <path.tbl>                 # optional character map (relative to CWD)
find  <offset-hex> <len> <text>  # guard: abort unless the slot decodes to <text>
set   <offset-hex> <len> <text>  # replace the slot (encoded <= len, padded)
menu  <name> <offset-hex> <len> <text>   # named menu-item replacement
```

## Quick start

```sh
# Build everything
./build-all.sh

# Inspect a ROM you own
c/nes-edit info your.nes

# Dump a text slot (ASCII, or with a character table)
c/nes-edit dump your.nes 1A2C 16
c/nes-edit dump your.nes 1A2C 16 your.tbl

# Apply an edit script to a working copy (originals stay untouched)
c/nes-edit apply your.nes edits.edit your.edited.nes
```

The C++ (`cpp/nes-edit-cpp`) and Java (`NesEditCli`) tools take identical
arguments. See [`docs/WORKFLOW.md`](docs/WORKFLOW.md) for a full worked example
on the synthetic sample ROM, and [`docs/FORMAT.md`](docs/FORMAT.md) for the iNES
format and the editing model.

## Strategy — "thinking games"

Strategy / puzzle / RPG titles are the richest target: menus, item names, spell
lists, map labels, and dialogue are all fixed-width PRG-ROM strings. The
recommended loop is **dump → script → apply → verify**; the length invariant
guarantees each rename stays within its slot so the ROM remains valid. The
SLeeLa model (`sleela/NesEditModel.sleela`) is built to reason about exactly
these edits before a single byte is written.


## ROM analysis workbench

The `analysis/` directory also contains a read-only Python analysis pipeline and native C/C++ tools. From this directory:

```sh
# Build six native executables for the current OS
make release-binaries

# Run Python, native-build, and CLI tests
make test

# Build an analysis workspace from a ROM you own
python3 analysis/nes_dev_environment.py /path/to/game.nes --title "Research Title"

# Native header inspection and linear-sweep disassembly
build/nes-native-c /path/to/game.nes
build/nes-disasm-c --out-dir ./private-analysis /path/to/game.nes
build/nes-disasm-cpp --out-dir ./private-analysis /path/to/game.nes
```

The six native executables are `nes-native-c`, `nes-native-cpp`, `nes-rom-build-c`, `nes-rom-build-cpp`, `nes-disasm-c`, and `nes-disasm-cpp`. Make and CMake builds are supported. The GitHub Actions native workflow is configured for Linux, macOS, and Windows artifacts; verify the exact commit's Actions result rather than assuming a workflow configuration means the latest build passed.

The native disassemblers perform a conservative linear sweep over available PRG bytes. They do not emulate mapper state, prove instruction boundaries, or reconstruct original source. The Python workbench provides the broader workspace, trace, rules, and project-manifest workflow. See [the analysis guide](analysis/README.md), [native build guide](analysis/NATIVE-BUILD.md), and [round-trip guide](analysis/ROM-ROUND-TRIP.md).
